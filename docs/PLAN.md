# 幸福工厂生产统计 Mod 产品与技术规划

本文件定义后续 agent 的共同目标和实现约束。交付物是可安装、可在游戏中验证的 Mod：按 P 打开统计窗口，展示真实生产、消耗及电力历史。当前只完成规划，不把推测中的游戏 API 当作已验证能力。

## 1 已知条件与规划默认值

### 用户已明确的要求

- 游戏为《幸福工厂》，体验参考《异星工厂》的 Production statistics。
- 展示物品、流体、电力等统计状态，P 为默认打开按键。
- 每个页面参考当前工程图片，公共顶部以 `items.png` 为准：先时间按钮，再标签按钮。
- 本阶段产出可供后续 agent 执行的任务文档。
- 用户已确认先单人、再联机；支持游戏和 SML 的最新版；暂时没有可用于 Unreal 编译和实机验证的 Windows 电脑。
- 用户补充要求通过 ficsit.app 的 Satisfactory Mod Manager（SMM）管理本 Mod。
- 用户要求代码库托管在 GitHub 并开源；公开仓库是交付要求。
- 每项任务应用 ponytail full；代码检索优先 codegraph，其次 rtk。

### 工程检查结果

工程目前只有四张图片，没有源码、`.uproject`、`.uplugin` 或构建配置。本轮 codegraph 因只读数据库错误在重试后仍不可用；后续实现任务重新检查其可用性，失败时使用 rtk，不自行重建索引。

首版包含三个页面、九种时间范围、实际生产／消耗统计、电力概览与历史、历史随存档保存，以及完整的打开／关闭体验。统计范围默认整个存档世界，从安装并启用本 Mod 后开始，不追溯安装前数据。

| 时间 | 5s、1m、10m、1h、10h、50h、250h、1000h、All；默认 1m |

| 交互 | 搜索、排序、曲线显示选择、悬停读数、恢复显示选择 |
| 历史 | 关闭窗口继续收集；存档／读档恢复；大范围降低分辨率 |

## 4 统计口径与必须成立的不变量

### 4.1 物品与流体

统计“工厂完成的实际产出”和“工厂实际投入／消耗”，不使用配方理论产能冒充实际值。产出在产物实际生成时记录；消耗在原料实际不可逆投入生产或燃烧时记录。输入与输出可发生在周期的不同时间，短窗口内不要求两侧配方比例严格相等。

| 场景 | 规则 |
| --- | --- |
| 采矿机、抽水机、资源抽取设备 | 已实际产生的原料计产出；包括符合该语义的便携式采矿设备 |
| 加工机器 | 原料实际投入计消耗；实际产物计产出；多输入／多输出逐项记录 |
| 包装／解包 | 包装物进入物品页，液体／气体进入流体页，容器按实际输入输出统计 |
| 发电燃料和配套原料 | 实际燃烧／消耗计对应物品或流体消耗；废料等副产物计产出 |
| AWESOME Sink | 已实际销毁的物品计消耗，不计产出 |
| 传送带、管道、仓储、车辆装卸、维度仓库转移 | 只是搬运，不计生产或消耗 |
| 输入缓冲区收货／输出缓冲区出货 | 不是统计边界，不能仅凭库存增减计数 |
| 堵料、缺料、停机、停电 | 只有实际事件计数；没有事件不产生理论产量 |
| 超频、增产、替代配方、机器类型变化 | 以实际结果为准，不使用固定配方倍率推算 |
| 清空管道、删除物品、建造／拆除返还 | 首版不算工厂消耗／产出 |

物品内部优先使用原生整数数量和足够宽的累计类型；流体保留精度，并在已验证的原生单位到 m³ 边界统一换算。不能凭经验直接写固定换算系数。以游戏实际机器／管道读数对照验证，拒绝负数、NaN 和无穷值进入统计。

窗口平均速率：`窗口内实际数量 × 60 / 有效观测秒数`，单位分别为件/min、m³/min。有效观测秒数为该统计类别已覆盖的仿真时间；正常停机的已观测时间也计入分母。新出现的条目在已覆盖且无事件的历史时段为零，不能从首次生产开始缩短分母。没有有效时间时显示“尚无数据”。

已运行 20 秒却选择 1 分钟时，显示“已采集 20 秒”，按 20 秒计算并留出未知历史；不能暗中按 60 秒摊薄。采集失败不等于生产为零。产品语义不允许用理论值静默填补失败；无法采集的机器类型应列为覆盖缺口并阻止宣称完整支持。

### 4.2 电力

首版统计全世界全部电网。每个时刻先识别实际电路／电网，去重汇总，再形成世界总值。不同网络一边缺电一边富余不能被全局求和掩盖；概览额外显示跳闸／异常网络数。不把“全局供需相抵”描述为所有机器都获得供电。

| 指标 | 含义和单位 |
| --- | --- |
| 当前实际消耗 | 游戏电力系统实际读数，MW；与最大需求分开 |
| 当前发电／容量 | 实际发电与可用发电容量，MW；缺少容量时不得计算虚假比例 |
| 最大需求 | 若目标版本能可靠读取则展示，明确命名；不是实际消耗 |
| 已存能量／总容量 | MWh，展示绝对值与百分比；不能标成 MW |
| 充电／放电 | 两个独立非负功率指标，MW；储能不重复计入发电来源 |
| 历史功率 | 按真实仿真时间加权的平均功率，MW |
| 历史能量 | 如显示区间电量，`Σ(MW × 秒) / 3600`，MWh；储能曲线显示时点能量 |

电力三栏：消耗按消费者建筑类型，发电按发电建筑类型，储能按储能建筑类型分组。列表功率为所选区间加权均值；储能量为区间末端有效快照。图标上的机器数量表示当前在线统计覆盖的该类型设备数，必须在详情中说明，不伪装为历史平均数量。

T01 必须验证车辆、铁路、悬浮背包等特殊负载以及发电增益的归属。总电网值与已分类值的差额可作为明确标注的“未分类／电网调整”项；不得漏掉差额、钳制隐藏负差或编造设备归属。若 API 无法可靠分类，应报告证据并调整明细方案，不能替换为理论额定功率。

零容量显示“无容量／无储能”，不是 100%。网络拆分、合并、开关切换、跳闸后，世界总量不能重复计数；首版不保存按网络 ID 分裂的历史，也不提供单网选择，从而避免不稳定网络 ID 污染历史。

### 4.3 时间、窗口与历史

- 使用世界仿真时间；游戏真正暂停时不累计，菜单打开但世界继续运行时继续统计；离线不补产量。读档从存档里的统计时间恢复。
- 每个存档独立，读旧档后回到旧档时间线；不与未来历史、其他存档或主菜单数据合并。
- 数量是可累加事件，功率是需时间加权的状态，储能是时点状态。三者不能共用“直接相加”的降采样规则。
- 建议以 1 秒为基本采样／归桶节奏，显示刷新 1 秒一次。生产事件在发生时累加，不能因 1 秒采样遗漏快周期生产。
- 使用有界的多分辨率历史：初始候选为 1 秒保留 10 分钟、10 秒保留 1 小时、1 分钟保留 10 小时、10 分钟保留 50 小时、1 小时保留 1000 小时。T03 以容量测算决定最终参数，不做每秒永久追加数组。
- All 的数量累计必须精确且随档保存；全生命周期趋势另用有界逐级合并，最多约 512 点，明确显示实际时间范围和分辨率。All 不是最近 1000 小时的别名。
- 查询图表最多约 600 点／曲线；降采样合并数量与有效时长，功率保留积分及有效时长，储能保留末值；需要尖峰展示时额外保留 min/max。
- 多级桶重叠不能重复相加。选择一种合适分辨率或按不重叠时间段拼接；边界落在粗桶中时显示实际对齐的查询起止时间与“约”标记，不把分摊估计说成精确数量。
- 已观测且无事件的零值与未知缺口分开保存；长历史压缩仍保留覆盖标记。历史不足时可点击长时间按钮，但明确显示实际覆盖。

## 5 最小架构与数据流

采用一个原生 Unreal/SML 插件。建议 C++ 负责采集、时间序列和存档数据，UMG 负责窗口与列表，少量自绘控件负责折线图。先检查游戏或已有依赖中是否有合适图表控件；没有时才实现一个共用图表控件。不引入网页渲染或通用插件框架。

```text
权威世界的真实生产事件 ─┐
权威世界的电力快照 ───┴→ 统计子系统 → 有界历史 → 查询结果 → 本地窗口
                               ↕
                         游戏存档生命周期
本地 P 输入 → 游戏原生 UI 栈 → 打开／关闭窗口
```

职责划分是逻辑边界，不要求一职责一服务／接口：

| 逻辑职责 | 所有权 |
| --- | --- |
| 版本相关采集 | 在真实事件边界读取数量；电力读取；单位换算；有限的游戏版本耦合 |
| 统计子系统 | 一份权威状态、生命周期、时间推进、查询与保存协调 |
| 历史结构 | 桶累计、降采样、查询、覆盖信息；不引用 Widget |
| 本地窗口 | 用户选择、输入、格式化与渲染；不扫描机器，不修改统计事实 |

SML 已提供可管理世界级状态的 Mod Subsystem，可按其机制注册和选择复制策略，避免自建全局管理器。[Mod Subsystems 文档](https://docs.ficsit.app/satisfactory-modding/latest/Development/ModLoader/Subsystems.html)

默认键和重绑定沿用游戏的 Enhanced Input 接入。其文档明确包含版本迁移待更新内容，因此 T00/T06 要以锁定版本的头文件、示例和实机结果确认资产类型及注册方式。[Enhanced Input 文档](https://docs.ficsit.app/satisfactory-modding/latest/Development/Satisfactory/EnhancedInputSystem.html)

采集方式按顺序选择：已有可信实际累计／事件 → 已有 delegate → 必要的 SML hook。Native Hook 与 Blueprint Hook 的机制和版本约束不同；只观察经过验证的实际成功操作，不取消或改写原游戏行为，也不能把“after 被调用”本身当成生产成功证据。[Native Hooking 文档](https://docs.ficsit.app/satisfactory-modding/latest/Development/Cpp/hooking.html)

每个真实事件只计一次，避免同时 hook 机器和库存底层后重复累计。验证回调线程；若发生在工厂工作线程，先把不含危险 UObject 访问的最小数据交给安全队列，回到游戏线程更新子系统。只有证据显示需要时才加队列；不能直接在未知线程修改共享容器。世界退出后禁止遗留回调继续写入。

### 数据契约

T02 将以下语义落成一份实际 C++ 类型定义，名称可按工程风格调整；这里不是对现有游戏 API 的声明。

| 数据 | 必需字段 |
| --- | --- |
| 序列标识 | 类别、物品描述资源稳定标识或电力分组、指标、产出／消耗方向 |
| 数量输入 | 序列、仿真时间、成功数量、明确单位、来源覆盖类别 |
| 电力输入 | 仿真时间、各功率／容量／能量值、有效状态、分组及未分类量 |
| 历史桶 | 起止时间、覆盖时间／缺口、数量或功率积分或状态末值，按指标定义 |
| 查询 | 类别、窗口、可选序列、点数上限；返回实际起止时间和分辨率 |
| 展示结果 | 名称／图标标识、窗口累计、均值或末值、曲线、单位、质量状态 |
| 保存数据 | schema 版本、统计起点和时钟、累计、各级桶、覆盖、稳定资源标识 |

不保存 UObject 裸指针或临时电网 ID。物品资源缺失时保留其历史数量，用替代图标和“未知物品”提示，不阻止读档。存档结构利用游戏保存机制，先验证实际序列化链路；不能假定只写一个 SaveGame 标记就已经持久化。

## 6 开发阶段与发布门槛

| 阶段 | 结果 | 进入下一阶段前的证据 |
| --- | --- | --- |
| 环境和探针 | 空插件可加载；真实数量／电力 API 可读取 | 精确版本记录、构建日志、受控场景实测 |
| 最小纵向链路 | 一个真实物品事件，经统计查询，在 P 窗口显示 | 堵料／停电／关窗后仍正确；没有重复计数 |
| 三页与完整历史 | 物品、流体、电力；全部时间按钮；搜索和曲线 | 契约测试、三页实机截图、覆盖清单 |
| 持久化和加固 | 保存恢复、缺口／错误展示、性能符合预算 | 重启加载、旧档、长时间合成测试、性能报告 |
| 可安装发布包 | 源码、必要资产、构建步骤、测试记录、Mod 包 | 清洁环境安装和卸载回归；未验证能力明确列出 |

候选性能预算不是已测事实：在指定验收机器、约 10,000 台相关设备、最多 500 个活跃统计序列下，关闭 UI 的额外游戏线程耗时 p95 目标低于 1ms／帧，打开 UI 的额外耗时目标低于 2ms／帧；统计内存和存档增量各以 128MiB 为初始上限。T00/T03 先记录机器、场景、序列定义与内存测算，T09 实测并解释任何调整。必须同时计入 hook 和后台线程成本，不能只测 UI。

不要每帧遍历全世界 Actor；优先已存在设备／电网注册表和生命周期通知。确需一次启动发现或定时设备扫描时，记录规模上限和升级条件，并证明不会随运行小时数增长。

## 8 SMM 管理与发布要求

SMM 是用户安装管理器，SML 是游戏内加载及扩展机制，SMR 是 ficsit.app 的 Mod 仓库；本项目使用这条标准分发链，不额外开发一个管理器。[发布文档](https://docs.ficsit.app/satisfactory-modding/latest/Development/BeginnersGuide/ReleaseMod.html)

GitHub 是源码和版本记录的主仓库，SMR／SMM 是玩家安装管理入口，两者都要交付。源码仓库应包含实际 C++、本 Mod 必需的自有 `.uasset`、配置、构建说明、验证说明、许可证和需要的第三方说明。引擎二进制、游戏原始资源、下载依赖、凭据、个人存档、Intermediate／Saved／派生缓存不进入公开仓库。根目录参考图只用于设计参考，在未明确其再分发条件前默认不推送；公开说明可改用本 Mod 自己的截图。

必要的二进制源资产较大时使用 Git LFS，并确保贡献者能按文档取得它们。不要仅上传C++却遗漏运行所需UMG／输入资产，也不通过发布整套引擎来实现可复现构建。公开仓库需真实 LICENSE，具体许可证由用户确定；尚未选择时不得宣称已完成开源交付。

每次发行建立与 Mod 语义版本一致的 Git tag，记录对应源码提交、构建环境、发行说明及实际安装包位置；SMR 的源码链接指向真实公开仓库。GitHub Release 可镜像候选／正式安装包，但不能替代 SMM 分发验收。用户已明确授权 GitHub 公开开源，后续不重复询问是否开源；建库前落实账号／组织、仓库名、许可证和必要访问权限即可。

- 插件描述中维护固定 Mod Reference、名称、作者、说明、语义版本、游戏 build 兼容约束及必需 SML 依赖；准确声明运行模块及内容资产，由匹配版本的 Alpakit 生成发布包。
- 不照抄旧教程中的输出目录或示例版本范围；T09 检查实际生成的包和元数据，不提交占位作者、假链接或未经测试的兼容承诺。
- 用受支持的开发／测试安装流程完成预发布包验证。能手动装入 Mods 目录并不等于已验证 SMM 管理；如果当前 SMM 不支持本地导入，记录这一限制并通过 SMR 测试发行验证，不编造本地导入功能。
- T11 准备 ficsit.app 页面、图标、截图、发行说明、兼容状态和版本文件，并在正式上传流程可用后测试 SMM 获取。页面明确首版仅支持单人及生产覆盖边界。
- 升级验收使用两个真实版本，验证 SMM 提供新版本、正确替换文件、保留用户键位以及统计存档可读。兼容约束不能为“永远支持将来所有版本”。
- SMM 禁用／卸载不等于永久保留 Mod 历史：游戏可能在禁用 Mod 后另存时去掉扩展数据。必须实测并说明，不能承诺重新启用一定找回历史。测试使用备份存档。
- 当前请求为规划，不上传或公开发行。后续先完成可审阅的包和页面材料，再按用户授权进行发布；没有账号、有效包或审批状态时将 T11 保持未完成。

完整的“可被普通玩家从 SMM 获取并管理”交付需要 T11；只有 T09 完成时，应称为已打包并完成本地验证，不能称为已经上架。[上传 SMR 文档](https://docs.ficsit.app/satisfactory-modding/latest/UploadToSMR.html)
